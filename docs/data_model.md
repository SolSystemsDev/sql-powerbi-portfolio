# Module 1 — Data Model and Lineage

All six data sources are generated by `src/finance_portfolio/generator.py` with seed 42. They do not derive from an actual business, ERP or finance system.

## Source model and grain

| Table | Grain | Primary key | Rows in v0.1 |
|---|---|---|---:|
| `dim_department` | One row / department | `department_id` | 6 |
| `dim_gl_account` | One row / GL account | `gl_account_id` | 8 |
| `dim_date` | One row / calendar date | `date` | 730 |
| `fact_budget` | One row / fiscal month / department / GL | `budget_id`; unique composite month+department+GL | 1,152 |
| `fact_actual` | One row / expense transaction | `transaction_id` | 3,465 |

### Relationship design (logical star schema)

```text
                       dim_date (date)
                         |          |
             month_start |          | transaction_date
                         v          v
  dim_department --> fact_budget  fact_actual <-- dim_gl_account
          |                               |
          +-------------------------------+
                  shared dimensions
```

`dim_date` joins to the budget fact at the first day of each month and to the actual fact at the transaction date. `dim_department` and `dim_gl_account` join to both facts by ID. Use **single-direction one-to-many** filters from each dimension to each fact in Power BI. Avoid direct fact-to-fact relationships.

## ETL lineage

```text
Seeded synthetic generator
  └── data/synthetic/*.csv
         └── Python loader: type conversion + SQLite foreign key checks
               └── SQLite star schema + vw_monthly_variance
                     └── group-by: fiscal month, department, GL, class
                           ├── data/processed/*.csv
                           ├── data/processed/executive_kpis.json
                           └── reports/executive_dashboard.html + chart SVG
```

The SQLite view aggregates actual transactions to the monthly budget grain *before* joining to budget. This avoids transaction multiplication, a common mistake when joining monthly budgets directly to transaction lines.

## Fiscal year convention

- Fiscal year starts **October 1** and ends **September 30**.
- Fiscal year is named for the ending September. Oct 2025 to Sep 2026 is **FY2026**.
- Fiscal month index: Oct=1, Nov=2, Dec=3, Jan=4, ..., Sep=12.
- MTD: filter to a fiscal/calendar month; compare monthly actual vs budget at the monthly grain.
- Fiscal YTD: include months from fiscal index 1 through selected index N.
- Demo defaults: FY2026 months 1–12, i.e. full FY2026, not a partial current-month estimate.

## Money and variance conventions

- Source data stores **whole integer cents** to avoid financial rounding drift.
- Processed exports convert to **USD decimal strings with exactly two decimal places**.
- `variance = actual - budget` for expense reporting.
- Positive variance means **unfavorable overspending**; negative variance means **favorable underspending**.
- Percentage variance = `(actual - budget) / budget`, null if budget is zero.
- YTD variance % = `(SUM(actual) - SUM(budget)) / SUM(budget)`; **never average line-item percentages**.
- No revenue, accrual, journal reversal, encumbrance, or general-ledger balancing logic is represented in this v0.1 expense-only demo.

## Quality gates

1. Unique primary keys and budget-grain composite uniqueness.
2. GL expense categories allowed: Labor or Non-Labor.
3. Foreign-key integrity for every fact row.
4. Raw budget sum must equal view budget sum.
5. Raw actual sum must equal view actual sum.
6. View grain must not contain duplicate month-department-GL combinations.
7. Department, GL and class aggregates reconcile to executive totals.
8. Fiscal year rollover and partial FYTD calculations have automated tests.

## Exception rule

`unfavorable_exceptions.csv` flags individual month-department-GL rows with **variance ≥ $5,000** and **variance ≥ 20% of budget** (both must be true). These are illustrative screening thresholds, not statistical anomaly detection.
